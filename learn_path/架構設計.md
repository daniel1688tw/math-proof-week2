> `learn_path/` 包含兩個相互獨立的子系統，共用同一套硬體約束（RTX 4050 6 GiB VRAM）。
> 此文件描述整體架構設計、各元件的職責與相互關係、以及關鍵技術決策。
>
> **★ 2026-07 更新**：子系統 B 的**訓練資料策略已被取代**。原本的「行為遷移」策略
> （MathDial+GSM8K 小學算術資料）已被 `week3/dataset/` 的**手寫域內 grounded 資料集**取代，
> 訓練引擎（`train_qlora.py`、`common.py`）本身不變，只是改指向新資料。本文件第 3.2 節
> （資料準備）與第 6 節設計取捨中「行為遷移」相關敘述**僅供歷史對照**，新專案請讀

## 二、子系統 A：直接生成證明（Ollama 路線）

### 2.1 設計動機

| 問題 | 解法 |
|------|------|
| 本機 VPN 封鎖 HF 舊版 CDN，無法下載 safetensors | 改用 Ollama（自己的 registry，暢通）|
| transformers 5.x + bitsandbytes 在 Windows 載入 7B 時 segfault | Ollama 底層為 llama.cpp，完全繞開 transformers/bnb |
| Qwen2.5-Math-7B 是答案調優型，缺乏自我審查 | 換成 **Qwen3-4B-Thinking-2507**（RL 訓練，先 `<think>` 後作答）|
| 思考型模型在最難題會耗光 token 預算、答案被截斷 | 截斷偵測 + 兩輪自動續寫（見 2.4）|

### 2.2 資料流

```
raw_problem (str)
    │
    ▼
run_simple_4b_ollama()
    │  1. _resolve_model()          ← 讀 ollama_model.txt 決定 tag
    │  2. 組 messages（system + user）
    │  3. POST /api/chat (think=True)   ────►  本機 Ollama (llama.cpp)
    │  4. 解析 message.thinking / message.content
    │  5. 若 done_reason=="length" → 最多 2 輪續寫
    ▼
{ reasoning: str, answer: str, model: str }  或  answer: str
```

### 2.3 關鍵設定

| 參數 | 值 | 原因 |
|------|----|------|
| `TEMPERATURE / TOP_P / TOP_K` | `0.6 / 0.95 / 20` | Qwen 官方對思考模型的建議值；低溫導致退化（重複、繞圈）|
| `NUM_PREDICT` | 15360 | 最難題思考鏈可達 ~2 萬字元，需大預算 |
| `NUM_CTX` | 16384 | 實測 20480 致 KV cache + 權重達 6.0GB，30% offload 到 CPU，速度大降 |
| `REQUEST_TIMEOUT` | 1800s | 長思考題在 4050 可達數分鐘 |

### 2.4 截斷偵測與自動續寫

Ollama 回傳的 `done_reason` 為 `"stop"`（正常）或 `"length"`（截斷）。

```
if done_reason == "length":
    # 第 1 輪：關閉 think，要求直接輸出完整最終證明
    cont_messages = original_messages
                  + [assistant: 已生成內容]
                  + [user: "停止思考，輸出完整證明"]
    → resp2 (think=False)

    # 若第 1 輪仍截斷（罕見）：
    # 第 2 輪：要求從中斷處接著寫，並拼接
```

設計取捨：寧可壓低 NUM_CTX（保全 GPU）靠續寫補完，不靠加大 context 換取 CPU offload。

### 2.5 推理/答案分離（雙層保險）

1. **優先**：Ollama 結構化欄位 `message.thinking` + `message.content`（`think=True`）
2. **後援**：舊版 Ollama 把思考內嵌在 content 時，用 `_split_think()` 從 `</think>` 切割
3. **相容**：若模型拒絕 `think` 參數回 HTTP 400，自動移除後重送

## 三、子系統 B：蘇格拉底助教 QLoRA 微調

### 3.1 設計策略〔★ 已被 dataset/ 取代，見下方說明框〕

> **本節的「行為遷移」策略已停用**。實測發現訓練分布（小學算術，英文）與目標分布（大學
> 微積分，繁中）差距過大，微調模型在難題上會「自信給錯方向」（見
> `socratic_tutor/eval_out/v4/EVAL_REPORT_v4.md`：純微調在難題僅 2.90/5，最差且危險）。
> 新版改用 `week3/dataset/` 的**手寫域內 grounded 資料集**（50 題微積分證明 + 380+ 條
> 繁中蘇格拉底對話，system 帶參考解），訓練後純微調在同類難題達 4.25/5，不再有此失敗
> 模式。`train_qlora.py`／`common.py` 等訓練引擎程式碼不變，只需用環境變數把
> `TRAIN_JSONL`／`VAL_JSONL`／`ADAPTER_DIR` 指向 `dataset/` 底下的檔案即可，
> 見 `week3/CLAUDE.md`「執行方式」一節。以下 3.1～3.2 維持原文，僅供歷史對照。

「微積分證明 × 蘇格拉底引導」沒有現成資料集。本專案（舊版）採**行為遷移**策略：

```
引導行為       ←  數學教育資料（MathDial + GSM8K-socratic）
內容知識       ←  Qwen3-4B-Instruct 基底（已具備微積分能力）
行為錨定       ←  SYSTEM_SOCRATIC（推論時 system prompt）
```

**假設**：小學應用題上的蘇格拉底引導行為（問引導問題、不直接給答案、回應學生迷思）
可遷移至微積分證明，內容本身不需要從資料集學習。**此假設已被 dataset/ 的實驗結果部分推翻**
——行為確實可遷移，但缺乏 grounding 時內容知識不足會導致難題上給錯方向。

### 3.2 訓練資料準備（prepare_data.py，舊版）

| 資料集 | 筆數 | 格式 | 備註 |
|--------|------|------|------|
| `eth-nlped/mathdial` | ~2.3K（過濾後） | 多輪師生對話（Teacher / Student 輪替） | 真實引導行為；過濾超長對話（>4000 字元）與超多輪（>14 回）|
| `openai/gsm8k`（socratic split） | 1200 sampled | 單輪引導性子問題逐步分解 | 比重刻意壓低（占 1200/3500），避免模型學成「一次寫完整解答」|

**轉換流程**（MathDial）：

```
原始對話 (Teacher/Student 輪替)
    │
    ├── 去除動作標籤 "(probing)", "(telling)"
    ├── 去除學生姓名（避免模型記住訓練資料中的固定人名）
    ├── 合併連續同角色回合
    ▼
messages: [system, user(=學生+題目+錯誤嘗試), assistant(=老師), user, assistant, ...]
```

**輸出**：`data/train.jsonl`（~3100 筆）、`data/val.jsonl`（~130 筆），每行一個 messages dict。

### 3.3 QLoRA 訓練架構（train_qlora.py）

```
Qwen3-4B-Instruct（本機 qwen3_4b/）
    │
    ▼  BitsAndBytesConfig
4-bit nf4 量化載入（bnb_4bit_use_double_quant=True, compute_dtype=bf16）
    │
    ▼  prepare_model_for_kbit_training
啟用 gradient_checkpointing（use_reentrant=False）
    │
    ▼  LoraConfig(r=16, alpha=32, dropout=0.05)
套用 LoRA（7 個 projection 層：q/k/v/o/gate/up/down）
    │
    ▼  SocraticDataset + Collator
對話 tokenize（apply_chat_template → 固定序列長度 512）
只有 assistant 回合 token 計入 loss（其餘設為 -100）
    │
    ▼  Trainer（paged_adamw_8bit，lr=2e-4，cosine schedule）
訓練 2 epoch（共 484 步）
    │
    ▼
qlora_adapter/（adapter_model.safetensors + adapter_config.json）
```

**只有 assistant token 算 loss** 是關鍵：模型只學「如何回應」，不學「學生怎麼問」，
確保引導行為被強化，而非複誦輸入。

### 3.4 SocraticDataset：assistant-only masking 實作細節

```python
for i, msg in enumerate(messages):
    prefix = encode(messages[:i+1])
    new_tokens = prefix[len(input_ids):]
    if msg["role"] == "assistant":
        labels.extend(new_tokens)         # 計入 loss
    else:
        labels.extend([-100] * len(new_tokens))  # 不計入 loss
```

逐訊息遞增累積（非一次 tokenize），確保每個 token 的 assistant/non-assistant 歸屬精確。
截斷（MAX_LEN=512）後若 labels 全為 -100（無 assistant token），丟棄該樣本避免 loss=NaN。

### 3.5 顯存優化（6 GiB VRAM 限制下）

| 技術 | 效果 |
|------|------|
| 4-bit nf4 量化 | 基底模型 ~2.5 GiB（vs fp16 ~8 GiB）|
| LoRA（只訓練 adapter） | 可訓練參數 ~21M（vs 全量 4B）|
| gradient_checkpointing | 中間激活值重新計算，節省約 30% 激活顯存 |
| `MAX_LEN=512`（可由 `MAX_LEN` 環境變數覆寫） | 超過 512 截斷；實測 peak ~5.2 GiB（低於 6 GiB）|
| 分塊 CE（chunk=256 token） | 避免 Qwen3 詞表（15萬）× 序列長度的 fp32 升維 OOM |
| `paged_adamw_8bit`（可由 `OPTIM` 環境變數覆寫） | 優化器狀態分頁（8-bit + CPU offload on demand）|

> `MAX_LEN=1024` 會使保留池超過 6 GiB（碎片化 → 速度 4 倍慢且不可恢復），舊版固定用 512。
>
> **★ 2026-07 更新**：`dataset/` 的 grounded system prompt 因含完整 LaTeX 參考解，token 數
> 較長，實測**精簡系統提示規則後 `MAX_LEN=640` 仍可穩定訓練**（VRAM ~5.9GB，0 樣本被丟）。
> 另外，`paged_adamw_8bit` 若曾被 abrupt kill（如背景任務被強制中止），CUDA managed-memory
> 子系統可能損壞，重跑會在 step 0 出現 `bitsandbytes pythonInterface.cpp` init error；
> 此時改用非分頁的 `OPTIM=adamw_8bit` 即解決（LoRA 優化器狀態小，不分頁也夠用）。
> 亦新增 `NEFTUNE_ALPHA` 環境變數（設 5 啟用 NEFTune，對 embedding 加噪音，小資料 SFT
> 有感抑制過擬合）。`common.py` 的 `TRAIN_JSONL`／`VAL_JSONL`／`ADAPTER_DIR` 皆可由同名
> 環境變數覆寫，讓 `dataset/` 沿用同一套 `train_qlora.py` 而不需複製程式碼。

### 3.6 推論（inference.py）

```
基底模型（4-bit nf4）+ qlora_adapter/（PeftModel）
    │
    ▼  USE_ADAPTER=0 可跳過 adapter（對照微調前）
多輪互動（history = [system, user, assistant, user, ...]）
    │
    ▼  temperature=0.7, top_p=0.9, repetition_penalty=1.05
蘇格拉底回覆（引導問題，不直接給答案）
```

`reset` 指令清空對話歷史重新開始。adapter 在首輪後合併到基底，後續生成無額外延遲。

## 四、共用技術決策

### 4.1 模型選擇

| 位置 | 模型 | 理由 |
|------|------|------|
| 子系統 A | Qwen3-4B-Thinking-2507（Ollama） | 有思考鏈（`<think>`），推理品質更好；用 Ollama 繞開 bnb/transformers Windows 問題 |
| 子系統 B | Qwen3-4B-Instruct-2507（transformers） | 需要 Trainer API 做 SFT；4B 在 4-bit 下 6 GiB 可訓練；已驗證無 segfault |

### 4.2 本機模型路徑 vs HuggingFace 下載

`common.py` 的自動偵測邏輯：

```python
_LOCAL = "./qwen3_4b"
MODEL_NAME = _LOCAL if os.path.exists(f"{_LOCAL}/config.json") else HF_REPO
```

`download_chunked.py` 把模型分塊（8 MB）Range 下載到本機，繞過 VPN 對長連線的節流。
一旦本機有完整權重，所有腳本自動切換，不再連 HF。

### 4.3 Windows 環境避坑

| 問題 | 解法 |
|------|------|
| transformers 5.x + bitsandbytes 載入 7B segfault | 4B 實測 OK；7B 不用此路線（改用 Ollama）|
| pyarrow DLL 衝突（import 順序） | 在 `import torch` 前先 `import pyarrow, datasets` 預載 DLL |
| PYTHONNOUSERSITE 洩漏 | 所有腳本在進入點設定 `os.environ["PYTHONNOUSERSITE"]="1"` |
| PowerShell 中文路徑 NFC/NFD 歧義 | 用檔案工具操作而非 `cd`；腳本內用 `os.path.abspath(__file__)` 取絕對路徑 |

### 4.4 工具腳本職責

| 腳本 | 職責 |
|------|------|
| `_probe_env.py` | 印套件版本 + CUDA 狀態，投入訓練前的環境快速健檢 |
| `test_4bit_load.py` | 4-bit 載入 + 一次短推論，驗證 segfault 不會發生在 4B 模型上 |
| `probe_train_mem.py` | 14 步 dummy batch 訓練，逐步印 allocated/peak/reserved 顯存，診斷顯存雪崩原因（洩漏 vs 碎片化）|
| `download_chunked.py` | 分塊 Range 下載 Qwen3-4B safetensors，繞過 VPN 長連線節流，支援斷點續傳 |

## 五、執行流程

### 子系統 A（證明生成）

```powershell
# 前置：Ollama 已啟動且模型已 pull
ollama pull qwen3:4b
# 執行
conda run -n lora_project python "simple_4B_ollama copy 2.py"
```

### 子系統 B（蘇格拉底助教微調）

```powershell
Set-Location learn_path\socratic_tutor
$env:PYTHONNOUSERSITE = "1"

# 0. 環境健檢
conda run -n lora_project --live-stream python ..\\_probe_env.py

# 1. 資料準備（MathDial + GSM8K-socratic → train/val.jsonl）
conda run -n lora_project --live-stream python prepare_data.py

# 2. 煙霧測試（4-bit 載入 + 短推論，確認無 segfault）
conda run -n lora_project --live-stream python test_4bit_load.py

# 3. QLoRA 訓練（輸出 qlora_adapter/）
conda run -n lora_project --live-stream python train_qlora.py

# 4. 互動推論（微調後引導對話）
conda run -n lora_project --live-stream python inference.py
# 對照微調前：
$env:USE_ADAPTER = "0"
conda run -n lora_project --live-stream python inference.py

# 5. 前後對比輸出（3 題並排）
conda run -n lora_project --live-stream python compare.py
```

## 六、設計取捨小結

| 決策 | 取捨 |
|------|------|
| 使用行為遷移而非合成資料（舊版） | 零生成步驟、完全公開資料集、可快速上手；代價是訓練分布（小學應用題）與目標分布（微積分）有 gap，難題上會給錯方向。**已被 `dataset/` 手寫域內資料集取代**，見 3.1 節說明框。 |
| MAX_LEN=512（非 1024，舊版基準） | 穩定在 6 GiB 內；大多數多輪對話 <512 token 沒問題；極長對話截斷後仍保留前期引導回合。`dataset/` 因 system 含參考解，改用 640（精簡規則文字後仍穩）。|
| 只對 assistant 算 loss | 模型學「如何引導」而非「如何複誦學生問題」；是 SFT 蘇格拉底行為的核心設計，`dataset/` 沿用不變 |
| 分塊 CE（chunk=256） | 峰值顯存從 ~6.5 GiB 降至 ~5.2 GiB；代價是略增 Python 控制流開銷 |
| Ollama 路線（子系統 A）vs transformers 路線（子系統 B）| A 優先可靠性（繞開 bnb 問題）；B 需要 Trainer API 故選 transformers；兩路線使用同一基底模型但不衝突 |
| `dataset/` 用 grounded SFT + 分級提示規則（2026-07） | system 帶參考解讓引導方向永遠正確；學生連續卡兩次才透漏定理名稱，避免無限鬼打牆同時保留學生自主推導空間。詳見 `week3/CLAUDE.md`「資料集設計」。|

## 七、improve.md 修正：可信評估 + 正確性把關

針對 improve.md 指出的問題，新增以下機制（細節見 README「評估流程」與各檔 docstring）：

### 7.1 修評估資料洩漏（問題①）

- 題目集中到 `problems.py`：`CALCULUS_SEEDS`（**只進訓練集**）、`HELDOUT_PROBLEMS`（12 題、
  **不在訓練集**、評估泛化的主指標）。所有評估報告把 held-out（泛化）與 seed（記憶）分開。

### 7.2 教學品質評分（問題②）

- `eval_judge.py`：LLM-as-judge，把**參考解**一併給 judge，評 5 維（正確/相關/推進/不洩漏/
  聚焦，0–10）。`eval_common.score_form` 的形式分降級為「快速 sanity」，不再是唯一指標。

### 7.3 Solution-grounded 引導（問題③，核心架構改進）

```
題目 ──► 子系統 A 產完整證明（gen_reference_solutions.py / ollama_client.generate_proof）
        └─► 參考解（答案卡，學生看不到，存 eval_out/reference_solutions.json）
                                   │
題目 + 對話 ─────────────────────► build_grounded_system(參考解) 當引導層 system prompt
                                   └─► 老師「知道答案」→ 引導指向正確下一步、不洩漏
```

實作：`guided_tutor.py`（純 Ollama 互動）、`gen_ollama_replies.py grounded`（評估）、
`inference.py` 的 `REF_FILE`（給微調模型餵參考解）。把「會解」與「會教」解耦。

### 7.4 多輪 + 模擬學生評估（問題④）

- `eval_multiturn.py`：LLM 扮學生（會嘗試、會犯錯、一次只回一步），與助教對話數輪，
  再用 judge 評整段是否「引導到正確完成、引導正確、不過早給答案、能因應學生調整」。

### 7.5 資料格式與訓練健壯性（問題⑤⑥⑦⑨）

| 修正 | 內容 |
|------|------|
| GSM8K 多輪化（⑤） | `build_gsm8k_socratic` 改成「一問一等」多輪，不再把整條拆解塞進單一 assistant 訊息。 |
| 前綴依賴（⑦） | 種子每題做「帶/不帶 `STUDENT_NO_ATTEMPT_PREFIX`」兩版；`inference.py` 自動補綴預設關閉。 |
| 過擬合（⑥） | `train_qlora.py` 加 `load_best_model_at_end` + `EarlyStoppingCallback`（eval_loss 約 0.8 epoch 停滯）。 |
| 文件/死碼（⑨） | 統一 `MAX_LEN=512`；移除未使用的 `MemEfficientTrainer`；評估流程把子系統 A 的 socratic 模式納入基準對比。 |

### 7.6 評估流程的反競爭設計

所有評估「生成 → 存 JSON → 評分」三階段分離：transformers backend（base/finetuned）由
`compare.py` 產出，Ollama backend（A-socratic/grounded）由 `gen_ollama_replies.py` 產出，
最後 `score_replies.py` 讀 JSON 統一用 judge 評分。**避免 transformers 與 Ollama 同時佔用 6GB**。
