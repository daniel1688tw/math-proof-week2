## 下一輪迭代的建議優先序

### 優先級 1：不需重訓、可立即做

1. **B（宣告完成路由後盾）** —— 純 driver 改動，與既有 `review` 路徑同型，
   風險低、有明確測試方式（`test_driver_unit.py` 加案例 + 守門）
2. **商品化介面 F3 / N2** —— 下次觸碰 `app.py` 時順手（context manager、可讀性重構）

### 優先級 2：需要訓練實驗

3. **C/D/E 的增量訓練** —— 關鍵是**不要重複 v10/v11 的整批重訓**。
   v10/v11 兩次判退指向同一個交互作用：journey 資料的「連續多輪深入追問」訊號
   讓模型收尾後更傾向順勢多教。建議做法：
   - 只取 on-track（C）與 outline-refusal（E）樣本，**先不放 journey 旅程對話**
   - 加入「模型主動延伸→應收手」的負面對照樣本（對應 F）
   - 訓練後**必看 H5 案例**（e^x>1+x，均值定理）的收尾行為——這是兩次判退的共同重現點

### 優先級 3：需要新資源

4. **A（審閱解釋精確度）** —— 唯一的數學錯話來源，但 driver 蓋不住，需要訓練面或
   換一個更強的解釋產出者
5. **G（獨立驗證模型）** —— 換非同源模型當 VERIFIER，可同時提升備課可信度
   與 BoN 路線的重啟價值（`VERIFY=0` 是現行部署，程式碼與校準 harness 都保留著）

## 評估這些改動時的注意事項

| 注意 | 原因 |
|---|---|
| 對話類指標（Tier 3）**不能**當作採用依據 | n=3，四輪實測全幅亂跳，連現役模型都會被自己基準判退 |
| 質性內容跨多輪一致才算真問題 | v10 判退就是這樣認定的（H5 在 4 次獨立生成中全部重現）|
| 基準不可棘輪到幸運值 | 輸入隨機的指標要設在可辯護的真實水準 |
| 連跑兩輪守門之間 `ollama stop` | 否則 6GB 卡載入 4-bit 基底會 segfault |
| 跑守門前關 Antigravity IDE | 同上，背景進程搶 GPU |
