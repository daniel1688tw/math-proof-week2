## 下一輪迭代的建議優先序

### 優先級 0：新抓到、必須先處理

1. **#19 英文多輪洩漏** —— Tier 1b 一跑完就見底（4 題中 3 題）。這是招牌能力
   （抗洩漏）在多輪情境下的破口，且已有確定性指標可驗證修復。
   建議做法：先回放 `regression_scores/*_multiturn.json` 的英文對話，逐輪查
   `leaks_reference` 命中的是哪一段、當時的 level 與 phase，再決定是防護漏判還是別的成因。

### 優先級 1：不需重訓、可立即做

2. **#15（對話中途錯誤步驟）** —— 純 driver 改動，與既有 `review` 路徑同型，
   有明確測試方式（`test_driver_unit.py` 加案例 + 守門）。先量延遲可接受度。
3. **商品化介面 F3 / N2** —— 下次觸碰 `app.py` 時順手（context manager、可讀性重構）。
4. **B 的剩餘部分** —— 短宣告也路由後盾複核。

### 優先級 2：需要訓練實驗

5. **C/D/E 的增量訓練** —— 關鍵是**不要重複 v10/v11 的整批重訓**。
   兩次判退指向同一個交互作用：journey 資料的「連續多輪深入追問」訊號讓模型收尾後
   更傾向順勢多教。建議做法：
   - 只取 on-track（C）與 outline-refusal（E）樣本，**先不放 journey 旅程對話**
   - 加入「模型主動延伸→應收手」的負面對照樣本（對應 F）
   - 訓練後**必看 H5 案例**（e^x>1+x，均值定理）的收尾行為——兩次判退的共同重現點

### 優先級 3：需要新資源

6. **A（審閱解釋精確度）** —— 唯一的數學錯話來源，driver 蓋不住，需訓練面或換更強的解釋產出者
7. **G（獨立驗證模型）** —— 換非同源模型當 VERIFIER，可同時提升備課可信度、
   提示梯可信度與 BoN 路線的重啟價值（`VERIFY=0` 是現行部署，程式碼與 harness 都保留著）
8. **M（守門可靠度）** —— 加大 n 或改判準設計；在此之前**任何採用／判退決策都不可只用
   judge 分數當依據**

## 評估這些改動時的注意事項

| 注意 | 原因 |
|---|---|
| **判退時先跑 `measure_gate_noise.py`** | 9 個硬性 judge 指標中 8 個的純雜訊 ≥ 自己的 ε |
| **判退時先逐字比對 `*_replies.json`** | 全同 ⇒ 生成端沒變 ⇒ 波動都是評審雜訊 |
| 對話類指標（Tier 3）**不能**當作採用依據 | n=3，四輪實測全幅亂跳，連現役模型都會被自己基準判退 |
| **分數上升也不能當成修復有效的證據** | 近四輪 Tier 1/2 都是 104/104 逐字相同 |
| 質性內容跨多輪一致才算真問題 | v10 判退就是這樣認定的（H5 在 4 次獨立生成中全部重現）|
| 基準不可棘輪到幸運值 | 輸入隨機的指標要設在可辯護的真實水準 |
| **每條新不變式都要還原一次 bug 驗證會響** | `test_phase_routing.py` 的 V4 初版永遠不可能觸發 |
| 連跑兩輪守門之間 `ollama stop` | 否則 6GB 卡載入 4-bit 基底會 segfault |
| 跑守門前關 Antigravity IDE | 同上，背景進程搶 GPU |
| 連跑多輪 2 小時守門後讓機器休息 | walkthrough 探針處會出現進程層死結，立刻重試仍會卡同一位置 |
